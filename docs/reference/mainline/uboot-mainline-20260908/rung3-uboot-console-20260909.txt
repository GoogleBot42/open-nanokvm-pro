CONFIG_PRE_CONSOLE_BUFFER (0x480e8000) from the next boot.

Both captures are the SHIPPING image plus one change: `.#uboot-mainline-tee`
copies every console write into the pre-console buffer and takes nothing away
(serial output and console input both stay live), so the boot behaves exactly
as the product's does. `.#uboot-mainline-trace` is the other variant -- it
clears GD_FLG_HAVE_CONSOLE instead, which also disables tstc()/getchar(), so
it is NOT safe to draw conclusions from about a failing boot.

READ IT LIKE THIS. The 1 MiB environment read is the first data transfer of
the boot and, with `cdns,single-block-only` (#91), 2048 separate single-block
commands. One times out. The recovery is a card re-init, and
mmc_select_mode_and_width() walks down towards the legacy modes, which ask for
3.3 V I/O signalling -- nine mode candidates, nine refusals, because this
board's vqmmc is a FIXED 1.8 V rail. The card ends with no mode selected and
no block device, and every read after that is degraded: the 689-byte
extlinux.conf takes three attempts, the 48.8 MiB kernel never arrives.
`mmc rescan` in front of each retry cannot help -- it is the same re-init.

The slot register afterwards reads 0xB00000xx: bits 28 (preboot), 29
(extlinux attempted) and 31 (nothing booted), and the low bits show the SPL
had moved to slot B. Which is the fallback working: slot B still held the
vendor-derived U-Boot, and the appliance came up on it.
