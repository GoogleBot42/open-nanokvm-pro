## 1. Topology

Two identical instances, one per CPU core:

| Instance | Block base | Length | GIC | Affinity | DT label |
|---|---|---|---|---|---|
| wdt0 | `0x0484_0000` | `0x400` | `GIC_SPI 149` (hwirq 181), level-high | CPU0 | `wdt0` |
| wdt2 | `0x0604_0000` | `0x400` | `GIC_SPI 150` (hwirq 182), level-high | CPU1 | `wdt2` |

V: `AX620E.dtsi:375-402` for both nodes, both `status = "okay"` on this board
(`AX630C_emmc_arm64_k419_sipeed_nanokvm.dts:296-302`). V: `[D]/iomem.txt:10,19`
shows `04840000-048403ff` and `06040000-060403ff` live; `[D]/interrupts.txt:5-6`
shows `GIC-0 181` bound to CPU0 and `GIC-0 182` bound to CPU1, both named

evidence for the two-stage model.

Both instances take their clocks, clock-source mux and resets from the **peripheral
syscon at `0x0487_0000`** (§7). There is no wdt1 anywhere in the SoC's DT.

Whatever is said below about wdt0 applies bit-for-bit to wdt2 with the syscon bit
numbers shifted (§7 table).

## 2. Register map of the watchdog block

All offsets are from the instance base (`0x4840000` or `0x6040000`). Every
register is 32 bits and accessed with plain 32-bit load/store. **Nothing in the
block is ever read-modify-written** by the vendor driver or by any bootloader —
every write is a whole-word write of a literal (V, all writes in `ax_wdt.c` and
`ax620e.c:97-127`).

| Offset | Name used here | Access | Field / value semantics |
|---|---|---|---|
| `0x00` | `WDT_EN` | RW | bit 0 = watchdog enable. Write `1` to run, `0` to stop. Bits 31:1 unused (always written 0). Readable: the vendor reads it back to learn whether the dog is running. |
| `0x0C` | `WDT_TORR` | RW | bits 15:0 = timeout reload, **in units of 65536 counter ticks** (i.e. the high half of a 32-bit reload). Linear, not an index. Bits 31:16 unused (the driver's arithmetic can never set them). |
| `0x18` | `WDT_TORR_LOAD` | W | bit 0 = load strobe for `WDT_TORR`. Level-sensitive: write `1`, hold ≥1 counter-clock period, write `0`. |
| `0x24` | `WDT_CCVR` | RO | 32-bit current down-count, in **raw counter ticks** (not `TORR` units). |
| `0x30` | `WDT_CRR` | W | Counter-restart ("kick"). Level-sensitive: write the magic `0x6169_6370`, hold ≥1 counter-clock period, write `0`. Any other value is ignored. |
| `0x3C` | `WDT_INTR_CLR` | W | bit 0 = write 1 to clear the pending watchdog interrupt. |
| `0x54` | `WDT_INTR_EN` | RW | bit 0 = interrupt enable. Written `1`; never written `0` by anything. |

V for every offset, width and value: `ax_wdt.c:24-34` (the symbol definitions),
plus their uses at `ax_wdt.c:82` (`WDT_EN` read), `88-91` (`WDT_CRR` magic then 0),
`159-162` (`WDT_TORR` then the `WDT_TORR_LOAD` 1/delay/0 strobe), `181`
(`WDT_INTR_CLR`), `188` (`WDT_INTR_EN`), `194-197` (`WDT_EN` 1/0), `234`
(`WDT_CCVR`). V for the bootloader's independent agreement on `0x00`, `0x0C` and
`0x18`: `ax620e.h:123-125` and `ax620e.c:99-110`.

**Offsets not touched by anything:** `0x04`, `0x08`, `0x10`, `0x14`, `0x1C`,
`0x20`, `0x28`, `0x2C`, `0x34`, `0x38`, `0x40`, `0x44`, `0x48`, `0x4C`, `0x50`,
and everything from `0x58` to `0x3FF`.

### 2.1 Why the offsets are a `0xC` stride (I)

The seven used offsets are `0x00, 0x0C, 0x18, 0x24, 0x30, 0x3C, 0x54` — every
one a multiple of `0xC`, with `0x48` the only skipped slot. That is exactly the
**`{VALUE, SET-alias, CLR-alias}` triplet layout** this SoC uses in its clock
syscons and its pinctrl pad table (documented in `clk-model-20260906.md` §1.3 and
`pinctrl-model-20260906.md` §1, both **V** there). So the block is almost
certainly eight logical registers at slot indices 0–7, each occupying `+0x0`
(value), `+0x4` (write-1-to-set) and `+0x8` (write-1-to-clear), with slot 6
(`0x48`) unused.

This is **I**, and it is not load-bearing: both the vendor driver and the
bootloader only ever write whole values to the slot-0 word, and that demonstrably
works. Do not rely on the aliases without measuring them. (If they are real, the
`WDT_EN` set alias at `0x04` and clear alias at `0x08` would be the race-free way
to start/stop, and slot 6 at `0x48` is worth a read on hardware — it is the one
plausible home for a status/"which stage fired" register, which the vendor driver
never reads.)

## 3. The counting model

### 3.1 Clock

The counter is fed by a **1-bit mux in the peripheral syscon**, not by anything
inside the block:

- mux clear ⇒ the slow clock, which the driver calls `AX_WDT_CLK_32K` and
  hard-codes as **32 000 Hz** (V, `ax_wdt.c:39`).
- mux set ⇒ **24 000 000 Hz** (V, `ax_wdt.c:40`; V, `ax620e.h:126`
  `WDT0_CLK_FREQ` = 24000000).

The mux is periph-syscon `CLK_MUX0` (`0x4870000 + 0x00`) bit **19** for wdt0 and
bit **20** for wdt2, driven through its set/clear aliases at `+0xA8`/`+0xAC`
(V, `AX620E.dtsi:382,396` `clk_set = <0xA8 0xAC 19>` / `<... 20>`;
V, `ax_wdt.c:97-102`; V, `ax620e.c:105,122` writes `BIT(19)` to `+0xA8`).

**The real slow clock is 32 768 Hz, not 32 000** (I). The SoC's only 32 kHz root
is `rtc_out_32k` = 32768 Hz (V, `clk-model-20260906.md` §2.2.1), and the sibling
periph mux `clk_timer_sel` has parents `{rtc_out_32k, cpll_24m}` in that index
order (V, same file §2.7) — the wdt mux is the same shape. Consequence: every
timeout the vendor driver computes at "32000" comes out **2.34 % short** in wall
time. Harmless for a watchdog, but a mainline driver should take the rate from
`clk_get_rate()` and stop hard-coding it.

Which one is selected depends on who wrote last — and the vendor kernel and
U-Boot **disagree**. See §9.

### 3.2 The exact arithmetic

`WDT_TORR` is a **plain 16-bit linear count of 65536-tick units**. There is no
table and no log₂ index. The vendor's mapping from a timeout in seconds to the
register is (V, `ax_wdt.c:152-159`):

```
ticks = timeout_s * rate                  (64-bit)
TORR  = (ticks < 0xFFFFFFFF ? ticks : 0xFFFFFFFF) >> 16
```

i.e. `TORR = min(timeout_s × f, 2³²−1) >> 16`, truncating. The reload the
hardware actually uses is `TORR << 16`.

Two independent confirmations that the reload is `TORR << 16` and that `WDT_CCVR`
counts raw ticks:

- `get_timeleft` returns `WDT_CCVR / rate` with no `<<16` (V, `ax_wdt.c:234`) —
  so `WDT_CCVR` is in ticks while `WDT_TORR` is in 65536-tick units.
- the clamp constant is `0xFFFFFFFF` and it is shifted right by 16 before the
  write (V, `ax_wdt.c:36,158`) — a 32-bit counter with a 16-bit reload field.

**Representable timeouts.** `T(N) = N × 65536 / f` for `N` ∈ `[0, 65535]`:

| Counter clock | Granularity (`N`=1) | Max (`N`=65535) | `N` for the shipped defaults |
|---|---|---|---|
| 24 000 000 Hz | 2.7307 ms | 178.9542 s | 30 s ⇒ `N` = 10986 (`0x2AEA`) ⇒ 29.9991 s |
| 32 768 Hz (real slow clock) | 2.0000 s | 131 070 s ≈ 36.4 h | kernel's "90 s" ⇒ `N` = 43 ⇒ **86.000 s** |
| 32 000 Hz (what the driver assumes) | 2.048 s | 134 215.68 s | kernel's "90 s" ⇒ `N` = 43 ⇒ 88.064 s |

`N = 0` is legal and means **expire immediately** — that is the reset path (§6).

The vendor's advertised limits (V, `ax_wdt.c:105-107,437-439`) are
`min_timeout = DIV_ROUND_UP(0xFFFF, f)`, `max_timeout = 0xFFFFFFFF / f`,
`max_hw_heartbeat_ms = (0xFFFFFFFF / f) × 1000`. Both are slightly wrong and a
mainline port should not copy them: the true granularity is `65536/f` (so
`min_timeout` should be `DIV_ROUND_UP(65536, f)`), and the true maximum is
`0xFFFF0000 / f`, not `0xFFFFFFFF / f` (an overstatement of ~2 s at 32 kHz).
The `/f` before the `×1000` also throws away sub-second precision.

### 3.3 The 30 s U-Boot arm

U-Boot writes `(30 × 24 000 000) >> 16` = `10986` = `0x2AEA` into `WDT_TORR`
(V, `ax620e.c:100`), strobes `WDT_TORR_LOAD` 1 then 0 (V, `:101-102`), sets the
mux to 24 MHz (V, `:105`) and writes `WDT_EN` = 1 (V, `:108`). `10986 × 65536 /
24e6` = **29.9991 s per stage**. See §9 for the full boot-exit state and §5 for
why the wall-clock budget to a reboot is 30 s or 60 s depending on an unresolved
question.

`set_wdt0_timeout(t)` (V, `ax620e.c:114-127`) programs **`t/2`**, not `t` — the
one caller passes 180 and gets `N` = 32958, i.e. 90 s per stage (V,
`[S]/boot/uboot/u-boot-2020.04/cmd/axera/setup_boot/setup_boot.c:249`). That
factor of two is not a bug; it is the two-stage model (§5).

## 4. The kick / ping sequence

Three writes, in this order, on `WDT_CRR` (`+0x30`) (V, `ax_wdt.c:85-92`):

1. write the magic `0x6169_6370` (a 32-bit literal; as little-endian bytes it
   spells `pcia`),
2. delay,
3. write `0`.

The delay is `1 µs` when the counter clock is 24 MHz and `40 µs` when it is the
slow clock (V, `ax_wdt.c:38,98,101,370-373`). Both are comfortably longer than
one counter-clock period (41.7 ns and 30.5 µs), which is what the delay is for:
`WDT_CRR` is **level-sensitive across a clock-domain crossing**, not a
write-1-pulse register (I — the assert/delay/deassert shape plus a delay chosen
per counter frequency admits no other reading).

No read-modify-write, no ordering constraint against any other register, no
unlock sequence. Writing anything other than the magic is a no-op, so the
trailing `0` is safe.

The identical shape applies to `WDT_TORR_LOAD` (`+0x18`): write `1`, same delay,
write `0` (V, `ax_wdt.c:160-162`). **U-Boot omits that delay** (V,
`ax620e.c:101-102,119-120`) and gets away with it only because it always runs the
counter at 24 MHz, where one tick is 41.7 ns and two back-to-back APB writes to
the same peripheral cannot be that close (I). A mainline driver must keep the
delay: at 32 kHz, omitting it would silently fail to latch the timeout.

`WDT_TORR_LOAD` latches the new timeout. Whether it *also* reloads the running
counter is a **GAP** — the kernel always follows it with a kick (V,
`ax_wdt.c:163`), so the question never arises there; U-Boot does not kick at all
and still works, which suggests the strobe reloads (I, weak). Follow the kernel:
load, then kick.

## 5. Two-stage behaviour

**The block interrupts on the first expiry and resets on the second.** The reset
therefore happens at **2× the programmed timeout**.

Evidence:

- V: `set_wdt0_timeout(t)` programs `t/2` (`ax620e.c:116`) — the caller's units
  are wall-clock-to-reset, the register's are per-stage.
- V: the driver's own `/proc/ax_proc/wdt<N>_keep_alive` prints
  `"suspend timeout <keep_alive> suspend reboot time <keep_alive × 2>"`
  (`ax_wdt.c:316-321`). The DT sets `keep-alive = <175>` (V,
  `AX620E.dtsi:381,395`), so the vendor's own model is "programmed 175 ⇒ reboot
  at 350".
- V (device): `[D]/interrupts.txt:5-6` — both instances have taken **1159**
  watchdog interrupts each and the machine did not reboot. An expiry that reset
  directly could not produce that. Consistency check: at the shipped default
  (90 s requested ⇒ `N` = 43 ⇒ 86.0 s per stage at 32 768 Hz), 1159 interrupts is
  ≈ 27.7 h of uptime, and both instances having the *same* count is exactly what
  two identically-programmed dogs armed at probe would show.

The conclusion "reset at 2×" is **I** — strongly supported by the three items
above, but no source states the hardware behaviour outright, and the device can
only witness stage 1 (the ISR always prevents stage 2). Treat 2× as the design
and 1× as the safe budget.

**GAP:** whether `WDT_INTR_EN` = 0 collapses this to a single-stage direct reset.
U-Boot arms the dog with `WDT_INTR_EN` untouched (i.e. 0) and expects a reset, but
nothing in any source says whether that reset lands at 30 s or 60 s. Budget 30 s.

### 5.1 What the vendor ISR does

The handler (V, `ax_wdt.c:178-184`) does exactly two things: it writes 1 to
`WDT_INTR_CLR` to drop the level-high line, then it **kicks the dog**. That is
the whole handler.

The consequence is worth stating plainly, because it defines what this watchdog
is for on this SoC: **the vendor watchdog pets itself from its own interrupt.**
It cannot detect a hung userspace, a hung init, or a deadlocked kernel thread. It
only fires when the CPU it is affine to can no longer take interrupts at all — a
per-CPU hard-hang detector. Nothing ever opens `/dev/watchdog` on the vendor
image.

That also explains the driver's `WDOG_HW_RUNNING` logic (V, `ax_wdt.c:455-456`):
the bit is set **only when there is no IRQ**. With the IRQ present — which is the
case on this board — the driver deliberately hides the fact that the hardware is
running, so the watchdog core does not start its own ping worker; the ISR is the
ping worker.

### 5.2 Pretimeout

**Not exposed.** `ax_wdt_ident.options` is
`WDIOF_KEEPALIVEPING | WDIOF_SETTIMEOUT | WDIOF_MAGICCLOSE` (V,
`ax_wdt.c:237-240`) — no `WDIOF_PRETIMEOUT`, no `.set_pretimeout` op.

The hardware could support one, but not independently: there is a single reload
register, so `pretimeout` is structurally pinned to `timeout / 2`. A mainline
driver that wants to expose it should present `wdd->timeout` = 2·T (time to
reset), `wdd->pretimeout` = T, both derived from the one `WDT_TORR` write, and
reject any `set_pretimeout` that is not exactly half.

## 6. The reset path

The vendor kernel reboots **through the watchdog**, because PSCI cannot.

- V: the TF-A platform port `[S]/boot/atf/.../plat/axera/ax620e/ax620e_pm.c`
  implements no `system_reset` and no `system_off` — the string does not occur in
  the file. `SYSTEM_RESET` therefore returns NOT_SUPPORTED.
- V: the vendor patched `machine_restart()` so the PSCI hook is dead code:
  `process.c:161-164` reads `if (0) arm_pm_restart(...); else do_kernel_restart(cmd);`
  where mainline 4.19 reads `if (arm_pm_restart)`. `psci_sys_reset` is the only
  thing that ever assigns `arm_pm_restart` on arm64 (V,
  `[K]/drivers/firmware/psci.c:562`), so the patch exists precisely to skip it and
  fall into the restart-handler chain.
- V: the watchdog registers itself into that chain at priority **128**
  (`ax_wdt.c:450`).

### 6.1 The restart handler, in order

V, `ax_wdt.c:219-230`:

1. **Switch the counter clock to 24 MHz.** This is `ax_wdt_clk_enable(24 MHz)`,
   which itself is: gate the counter clock off (periph EB0 clear alias), write
   the mux set alias to select 24 MHz, gate the counter clock back on, `udelay(1)`,
   then kick. (V, `ax_wdt.c:122-143`.)
2. **Program `WDT_TORR` = 0** — via the normal `set_timeout(0)` path, so:
   write `0` to `WDT_TORR`, strobe `WDT_TORR_LOAD` 1 / `udelay(1)` / 0, then kick.
   The kick reloads the counter from 0, so it expires immediately. (V,
   `ax_wdt.c:152-165,225`.)
3. **`mdelay(500)`**, then return 0.

There is no spin loop and no re-check. The 500 ms is the whole guarantee. If the
reset has not happened by then the handler returns, `do_kernel_restart()` runs
the next handler in the chain, and `machine_restart()` eventually falls through
to `printk("Reboot failed -- System halted")` and a `while (1)` (V,
`process.c:169-170`).

The clock switch in step 1 is not strictly required — a `TORR` of 0 expires
within one tick at any frequency — but at 24 MHz the two stages plus the
clock-domain synchronisers take microseconds instead of ~60 µs (I).

### 6.2 The reset output has a second enable, outside the block

**A watchdog expiry only resets the SoC if the "abort" controller lets it
through.** That gate lives in the *common* syscon at `0x0234_0000`:

| Register | Address | Bits |
|---|---|---|
| `COMM_ABORT_CFG` | `0x0234_00A8` | bit 0 `CHIP_RST_SW` (write 1 = software chip reset); bit 1 `SWRST_CLR`; bit 2 `THM_CLR`; bit 3 `WDT0_CLR`; bit 5 `WDT2_CLR`; bit 6 `THM_EN`; bit 7 **`WDT0_EN`**; bit 9 **`WDT2_EN`** |
| `COMM_ABORT_STATUS` | `0x0234_00B4` | last-reset cause: bit 0 swrst, bit 1 thermal, bit 2 **wdt0**, bit 4 **wdt2** |

V: `ax620e.h:77-81,109-119` for the addresses and bit names; V:
`ax620e.c:166-199` for the read/clear/enable sequence and the human-readable
decode of the status bits.

Both bootloaders set the enables. The SPL writes
`WDT2_EN | WDT0_EN | THM_EN` (V, `board.c:291`), and U-Boot's
`axera_get_boot_reason()` re-does it: a plain write of the four `*_CLR` bits
(`0x2E`) to acknowledge the previous cause, then a plain write of `0x2C0`
(bits 9, 7, 6) to enable (V, `ax620e.c:169-179`). Because both are plain writes,
**`COMM_ABORT_CFG` is exactly `0x0000_02C0` when Linux starts** (V, by
construction from those two writes).

The vendor kernel never touches this register. A mainline driver need not either
— but it must not clear it, and anyone debugging "the watchdog expires and
nothing happens" should look here first.

`COMM_ABORT_STATUS` is a free, already-correct **boot-reason source** for
mainline: a `reset-controller`/`syscon` reboot-mode or a `restart_handler`-adjacent
read gives "last boot was a wdt0 reset" with no new hardware knowledge.

### 6.3 A simpler alternative reset

U-Boot's own `reboot()` does **not** use the watchdog. It read-modify-writes
`CHIP_RST_SW` (bit 0) into `COMM_ABORT_CFG` and spins (V, `ax620e.c:136-156`).
For mainline that is a two-line `syscon-reboot` node on `0x0234_0000`, offset
`0xA8`, mask `BIT(0)` — no driver code at all. Recommended as a second restart
handler at *lower* priority than the watchdog, so `reboot` still works if the
watchdog node is disabled. **I** that it works from Linux: the register and bit
are V, but nothing has exercised this path from the kernel.

## 7. The second `reg` window (`0x4870000`, the peripheral syscon)

The vendor node's second `reg` entry is `<0x0 0x4870000 0x0 0x400>` (V,
`AX620E.dtsi:377-378`), `devm_ioremap`'d separately (V, `ax_wdt.c:351-361` —
note it maps `end - start` = `0x3FF`, an off-by-one that is harmless because
nothing above `0xF4` is used).

The driver takes **five** `<set_offset, clr_offset, bit>` triples from DT and does
nothing else with the window. It **never reads it** — every access is a
write-1-to-set or write-1-to-clear through an alias.

| DT property | Logical register | Value word | Set alias | Clear alias | wdt0 bit | wdt2 bit | What it is |
|---|---|---|---|---|---|---|---|
| `clk_set` | `CLK_MUX0` | `0x00` | `0xA8` | `0xAC` | 19 | 20 | counter-clock source: **set = 24 MHz, clear = 32 kHz** |
| `aclk` | `CLK_EB0` | `0x04` | `0xB0` | `0xB4` | 14 | 15 | **counter** clock gate (`CLK_WDT0_EB` id 19 / `CLK_WDT2_EB` id 18) |
| `pclk` | `CLK_EB3` | `0x10` | `0xC8` | `0xCC` | 19 | 20 | **APB** clock gate (`PCLK_WDT0_EB` id 99 / `PCLK_WDT2_EB` id 98) |
| `arst` | `SW_RST3` | — | `0xF0` | `0xF4` | 1 | 3 | counter-domain reset |
| `prst` | `SW_RST3` | — | `0xF0` | `0xF4` | 0 | 2 | APB-domain reset |

V for the triples: `AX620E.dtsi:382-386` (wdt0) and `:396-400` (wdt2). V for the
alias offsets naming those logical registers: `ax620e.h:84-101` and
`[S]/boot/bl1/common/include/chip_reg.h:72-89` (the two bootloaders agree
symbol-for-symbol). V for the DT property → alias mapping being
`<set, clear, bit>`: `ax_wdt.c:70-73` (`SET_SET=0, CLR_CLR=1, REG_SHIFT=2`) plus
every use.

The clock-ID identifications above are **V**, and they resolve two of the
`clk-model-20260906.md` §7 gaps:

- `CLK_EB0` bit 14 = `AX620X_CLK_WDT0_EB` (id 19) and bit 15 = `AX620X_CLK_WDT2_EB`
  (id 18): confirmed independently by TF-A, which masks `0x37FDF` when gating
  peripheral clocks for deep sleep with the comment *"don't clr clk_periph_24m and
  clk_wdt2_eb"* — the two clear bits in that mask are exactly bit 15 (id 18,
  `CLK_WDT2_EB`) and bit 5 (id 28, `CLK_PERIPH_24M_EB`) under the clock model's
  descending-ID rule (V, `periph_sys.h:10`; V,
  `[K]/include/dt-bindings/clock/ax620e-clock.h:414-415,425`).
- `CLK_MUX0` bits 19/20 = `CLK_WDT0_SEL` (id 3) / `CLK_WDT2_SEL` (id 2), **one bit
  each**. The clock model listed these as inferred; the watchdog DT and the
  bootloader's single-bit `BIT(19)` write make them V, and prove the field width
  is 1.
- `CLK_EB3` bits 19/20 = `PCLK_WDT0_EB` (id 99) / `PCLK_WDT2_EB` (id 98) — again
  exactly where the descending-ID rule predicts.

**Reset polarity.** For a 4-cell `axera,axera_reset_match` controller, assert =
write the bit to the *set* register, deassert = write the bit to the *clear*
register (V, `axera_reset.c:109-127,157-194`; the periph controller is 4-cell, V
`AX620E_resets.dtsi:86-90`). So **1 = held in reset**. The watchdog driver calls
its reset helper with `en = 0` at probe (V, `ax_wdt.c:453`), i.e. it writes both
bits to the *clear* alias `0xF4` — it releases, it does not assert. Order is
`arst` then `prst` on release, `prst` then `arst` on assert (V, `ax_wdt.c:111-119`).

### 7.1 Can mainline drop the window? Yes.

**Required for the block to count and reset:** the counter clock gate on
(`CLK_EB0` bit 14), the APB gate on (`CLK_EB3` bit 19), both `SW_RST3` bits
released, and — outside this window — `COMM_ABORT_CFG` bit 7 set (§6.2).

**All four are already in that state when Linux starts on this board:**

- `CLK_EB0` bit 14 is set by the SPL immediately before every stage jump (V,
  `board.c:308-315` — `wtd_enable()` toggles *only* this bit; V,
  `[S]/boot/bl1/spl/spl_main.c:61,75,83` and
  `[S]/boot/bl1/core/boot/boot.c:1003`).
- `CLK_EB3` bit 19 and the two `SW_RST3` bits are never written by SPL, U-Boot or
  TF-A, yet U-Boot successfully programs `WDT_EN`/`WDT_TORR` from `chip_init()`
  onward — so the APB clock is running and both resets are released out of chip
  reset (**I**, but the reasoning is airtight: those writes could not land
  otherwise).
- `COMM_ABORT_CFG` = `0x2C0` (V, §6.2).

The vendor driver's syscon writes are consequently either no-ops (the two reset
releases) or optional policy (the mux, and a gate-off/gate-on cycle it only does
in order to change the mux safely). **Skipping the whole second window is safe on
this board**, provided the driver does not want to change the counter frequency.

Recommended mainline binding instead:

```
watchdog@4840000 {
        compatible = "axera,ax630c-wdt";
        reg = <0x0 0x4840000 0x0 0x400>;
        interrupts = <GIC_SPI 149 IRQ_TYPE_LEVEL_HIGH>;
        clocks = <&periph_clk AX630C_CLK_WDT0_EB>,      /* counter */
                 <&periph_clk AX630C_PCLK_WDT0_EB>;     /* APB */
        clock-names = "wdt", "apb";
        assigned-clocks = <&periph_clk AX630C_CLK_WDT0_SEL>;
        assigned-clock-parents = <&periph_clk AX630C_CPLL_24M>;
        resets = <&periph_reset ...>, <&periph_reset ...>;
        reset-names = "wdt", "apb";
};
```

**Dependency to file against #80:** the peripheral clock driver currently
registers 21 of its 122 IDs, and *none* of `CLK_WDT0_SEL` (3), `CLK_WDT2_SEL` (2),
`CLK_WDT0_EB` (19), `CLK_WDT2_EB` (18), `PCLK_WDT0_EB` (99), `PCLK_WDT2_EB` (98)
is among them (V, `clk-model-20260906.md` §1.2 and §2.7). Every register position
those six need is pinned in the table above, so adding them is mechanical — but
until they exist, `clk_get()` on them returns a NULL clock and every
`clk_prepare_enable()` is a silent no-op (V, same file §1.2). That silence is
survivable here *only* because firmware already left the gates on. Do not let
#75 ship believing it enabled a clock it did not.

## 8. Interrupt

- wdt0: `GIC_SPI 149`, `IRQ_TYPE_LEVEL_HIGH` ⇒ GIC hwirq **181**.
- wdt2: `GIC_SPI 150`, `IRQ_TYPE_LEVEL_HIGH` ⇒ GIC hwirq **182**.

V: `AX620E.dtsi:379,393`; V (device): `[D]/interrupts.txt:5-6` shows exactly
`GIC-0 181 Level` and `GIC-0 182 Level`, both owned by `ax_wdt`.

The vendor requests it with `IRQF_SHARED` (V, `ax_wdt.c:395-397`) — pointlessly,
since nothing else is on those lines, but harmlessly.

Affinity is pinned from DT: the `cpu_flag` property (`<0>` for wdt0, `<1>` for
wdt2, V `AX620E.dtsi:380,394`) is fed straight to `irq_set_affinity(cpumask_of(flag))`
(V, `ax_wdt.c:392-393`), and the device confirms the split — 1159 counts on CPU0
for 181 and 1159 on CPU1 for 182. `WDT_INTR_EN` is written **only** when
`cpu_flag` is present (V, `ax_wdt.c:388-391`) — an odd coupling; on this board it
is always present so the interrupt is always enabled.

**Is the IRQ required?** For counting and for resetting, **no**. It is required
only for the vendor's self-petting behaviour (§5.1) and would be required for a
mainline pretimeout notification.

But there is a trap in the other direction: the line is **level-high and the
block latches it**. If a mainline driver enables `WDT_INTR_EN` and does not
install a handler that writes `WDT_INTR_CLR`, the first expiry asserts the line
permanently; genirq will spin on it, declare it spurious after 100 000 unhandled
occurrences, and disable it — and the second-stage reset then arrives anyway,
in the middle of an interrupt storm. **Either claim the IRQ and clear it, or
leave `WDT_INTR_EN` at 0.** A mainline driver that pets from the watchdog core
(the correct behaviour) should simply not enable the interrupt at all.

## 9. Boot-enabled state: what the firmware leaves programmed

### 9.1 SPL (`boot/bl1`)

The SPL's `wtd_enable(en)` touches **one bit and nothing else**: periph `CLK_EB0`
bit 14, via the set alias `0x4870000+0xB0` or the clear alias `+0xB4` (V,
`board.c:308-315`). It never writes the watchdog block — not `WDT_EN`, not
`WDT_TORR`. So the SPL's "arm" is purely *ungating the counter clock*; it is
called before every stage jump and at the start of `flash_boot()` (V,
`spl_main.c:59-84`, `boot.c:1003`), and disabled only when entering the USB/UART
download engine (V, `[S]/boot/bl1/core/fdl/fdl_channel.c:131`,
`[S]/boot/bl1/fdl/fdl_main.c:100`).

The SPL also sets `COMM_ABORT_CFG` = `WDT2_EN|WDT0_EN|THM_EN` (V, `board.c:291`).

**GAP:** whether the boot ROM leaves `WDT_EN` = 1 with some ROM-chosen `WDT_TORR`.
The SPL's comment ("make sure wtd enabled before jump") reads as if the block is
already enabled and only the clock needs restoring, but the SPL never writes the
enable bit and U-Boot's first act is to write it to 0 (below), so the question is
moot for Linux.

### 9.2 U-Boot

Three call sites matter:

- `chip_init()` calls `wdt0_enable(0)` early (V,
  `[S]/.../mach-axera/ax620e/chip_config.c:39`).
- `board_late_init()` calls `wdt0_enable(1)` (V, `ax620e.c:647`).
- `do_axera_boot()` calls `wdt0_enable(1)` with the comment *"Turn on watchdog
  before booting to kernel"* (V,
  `[S]/.../cmd/axera/boot/axera_boot.c:748-749`) — this is the last touch before
  the kernel image is read and `bootz`/`booti` runs.

Note that `wdt0_enable(false)` still programs `WDT_TORR` and the mux; only the
final `WDT_EN` write differs (V, `ax620e.c:97-111`). So even the "disable" paths
(autoboot aborted, memory dump, SD/USB update) leave `WDT_TORR` = `0x2AEA` and
the 24 MHz mux selected.

**State handed to `booti` on this board:**

| Location | Value |
|---|---|
| `0x4840000` `WDT_EN` | `1` — **running** |
| `0x484000C` `WDT_TORR` | `0x2AEA` (10986) ⇒ 29.9991 s per stage |
| `0x4840018` `WDT_TORR_LOAD` | `0` (strobed 1→0) |
| `0x4840054` `WDT_INTR_EN` | `0` — never written by any bootloader |
| periph `CLK_MUX0` bit 19 | `1` ⇒ counter clock = **24 MHz** |
| periph `CLK_EB0` bit 14 | `1` (SPL) |
| periph `CLK_EB3` bit 19 | `1` (reset default) |
| periph `SW_RST3` bits 1, 0 | `0`, `0` (released) |
| `COMM_ABORT_CFG` `0x23400A8` | `0x0000_02C0` |
| wdt2 (`0x6040000`) | **untouched by every bootloader** — `WDT_EN` presumably 0; counter-clock gate `CLK_EB0` bit 15 never set by SPL/U-Boot |

The autoboot abort path would disable it (V, `[S]/.../common/autoboot.c:305`) —
but this board has `bootdelay=0` and no usable console, so that path is
unreachable here.

**GAP:** wdt2's clock-gate state at boot. Nothing enables `CLK_EB0` bit 15; TF-A
takes care to *preserve* it across deep sleep, which implies it is normally on,
but that is not proof. A mainline driver for wdt2 must enable its clock
explicitly rather than assume.

### 9.3 What a mainline driver should therefore do at probe

**Report `WDOG_HW_RUNNING` for wdt0 and adopt a 30 s timeout** (or 60 s if the
two-stage model is confirmed on hardware) — the dog *is* running, has been since
before `booti`, and the counter is at 24 MHz.

The single most important line of the vendor probe is its **second** statement:
after `ioremap`, before anything else, it writes `WDT_EN` = 0 (V,
`ax_wdt.c:364`). That is what buys the rest of probe unlimited time. A mainline
driver should do the same — or, better, adopt the running dog properly:
`WDOG_HW_RUNNING` + `watchdog_init_timeout()` + a first kick, so there is no
window in which the board is unprotected. Do not, under any circumstances, leave
the dog armed at 30 s while deferring `watchdog_register_device()` on
`-EPROBE_DEFER`.

The vendor's full probe order, for reference (V, `ax_wdt.c:336-478`): ioremap
both windows → **disable** → read `clock-frequency` (absent on this board ⇒ 32 000)
→ create the procfs file → read `keep-alive` → `platform_get_irq` → if `cpu_flag`
present, write `WDT_INTR_EN` and set affinity → `request_irq` → read the five
syscon triples → fill `watchdog_device` (timeout 90, `watchdog_init_timeout`,
`nowayout`) → `watchdog_set_restart_priority(128)` → gate off / set mux / gate on
/ kick → release both resets → `set_timeout` + enable → set `WDOG_HW_RUNNING`
*only if there is no IRQ* → `watchdog_register_device`.

Do not port these defects from that probe:

- the error path after `request_irq` failure calls `watchdog_unregister_device(wdd)`
  on an uninitialised, never-registered `wdd` (V, `ax_wdt.c:398-401`);
- `devm_ioremap(dev, mem->start, mem->end - mem->start)` maps one byte short
  (V, `:359`);
- `g_ax_wdt[id]` is indexed by a file-static counter with no bound check against
  its 2 entries (V, `:76,458-460`);
- the `struct ax_wdt::timeout` member is never used.

## 10. What the block does *not* do

Things a naive port — especially one that starts from `dw_wdt.c` — would assume
and get wrong:

1. **`WDT_TORR` is not a log₂ index.** DesignWare's TORR encodes `2^(16+i)−1`; this
   one is a linear count of 65536-tick units. Writing an index gives a timeout
   65536× too short.
2. **The register offsets are not DesignWare's.** DW has CR `0x00`, TORR `0x04`,
   CCVR `0x08`, CRR `0x0C`, STAT `0x10`, EOI `0x14`. Here they are `0x00`, `0x0C`,
   `0x24`, `0x30`, and there is no EOI-on-read — the clear is an explicit write to
   `0x3C`.
3. **The kick magic is not `0x76`.** It is `0x6169_6370`, and it is a *level*, not
   a pulse: it must be written, held, then cleared (§4).
4. **There is no hardware nowayout and no lock register.** `WDT_EN` = 0 stops the
   dog at any time, from any state, with no unlock sequence — U-Boot does exactly
   that in six different code paths. `CONFIG_WATCHDOG_NOWAYOUT=y` in the vendor
   defconfig (V,
   `[K]/arch/arm64/configs/axera_AX630C_emmc_arm64_k419_sipeed_nanokvm_defconfig:2084`)
   is a pure software policy.
5. **Starting does not imply loading.** `WDT_EN` = 1 does not latch a new
   `WDT_TORR`; the load strobe at `0x18` does. The vendor always calls
   `set_timeout` *before* `enable` (V, `ax_wdt.c:202-210`).
6. **Stopping does not reset the counter.** Nothing observed re-zeroes `WDT_CCVR`
   on disable; the vendor's suspend/resume path reprograms and re-enables rather
   than relying on any preserved state (V, `ax_wdt.c:253-275`).
7. **The restart handler does not enable the dog.** It programs `WDT_TORR` = 0 and
   waits, assuming `WDT_EN` is already 1 (V, `ax_wdt.c:219-230`). If userspace had
   issued `WDIOS_DISABLECARD`, `reboot` would hang for 500 ms and then print
   "Reboot failed". A mainline port **must** write `WDT_EN` = 1 in its restart
   handler.
8. **The interrupt does not have to be claimed** — and on a mainline driver that
   pets from the watchdog core, it should not be enabled at all (§8).
9. **The reset can be vetoed outside the block** by `COMM_ABORT_CFG` bit 7 (§6.2).
10. **`min_timeout`/`max_timeout` as the vendor computes them are wrong** in both
    directions (§3.2).
11. **PSCI `SYSTEM_RESET` does not exist on this platform** (§6). A mainline kernel
    with `CONFIG_ARM_PSCI_FW` will register `psci_sys_reset` as `arm_pm_restart`
    and `machine_restart()` will call it *in preference to* the restart-handler
    chain — the opposite of the vendor's patched behaviour. Verify on hardware
    that `reboot` actually reboots; if it does not, the fix is a `syscon-reboot`
    node (§6.3) or a `psci` node removed from DT, not a kernel patch.

## 11. Risks for a first serial-less boot

This board has no usable console (`docs`: "No serial on this unit"), and
`bootdelay=0` means there is no U-Boot prompt to fall back to. Every failure mode
below looks identical from outside: the board reboots, or it does not come up.
Ranked by likelihood × cost.

1. **No watchdog driver at all ⇒ reboot loop, ~30 s after `booti`.** U-Boot arms
   wdt0 for 30 s per stage immediately before handing over (§9.2) and nothing
   else on the system pets it. A mainline kernel that reaches userspace in 20 s
   and then reboots at 30 s is *indistinguishable* from an early hang without
   serial. **Mitigation, and the thing to do first:** before testing anything
   else in #75, boot once with the watchdog node present and the driver's probe
   doing nothing but `WDT_EN` = 0. If that boot survives past 60 s, the entire
   class is eliminated. `docs/mainline-port.md` §"Trap 3" already flags this;
   this spec confirms the numbers.
2. **`WDT_TORR` written in raw ticks instead of 65536-tick units.** The field is
   16 bits wide, so the write silently keeps only the low half of the tick count
   — and the low half of a plausible number is usually tiny. A 90 s timeout at
   24 MHz gives `2 160 000 000 & 0xFFFF` = `0xFC00` ⇒ **2.7 ms**; at 32 768 Hz it
   gives `2 949 120 & 0xFFFF` = **0** ⇒ immediate reset. This is an instant,
   totally opaque reboot loop. Always `>> 16`.
3. **Frequency mismatch between the mux and the arithmetic.** If the driver
   computes for 24 MHz but the mux is on the 32 kHz source, every timeout is 732×
   longer (harmless). The reverse — computing for 32 kHz while the mux is at
   24 MHz, which is *exactly the state U-Boot leaves* — makes every timeout 732×
   **shorter**: a requested 60 s becomes 82 ms. **This is the most likely way to
   brick a first boot.** Read the mux, or write it explicitly, before the first
   `set_timeout`.
4. **`WDT_TORR` = 0.** Immediate reset. Guard `set_timeout` against a zero or
   sub-granularity request (anything under `65536/f` seconds truncates to 0).
   The only legitimate use of 0 is the restart handler.
5. **Omitting the `WDT_TORR_LOAD` strobe, or omitting its delay at 32 kHz.** The
   new timeout never latches and the dog keeps the old one — which after a
   U-Boot handover is 30 s. Reboot loop that survives every "but I set a 60 s
   timeout" check.
6. **Kicking with the wrong value, or forgetting the trailing 0.** Wrong value ⇒
   no kick ⇒ reboot at the old timeout. Forgetting the trailing 0 ⇒ **GAP**,
   plausibly holds the counter in reload forever, i.e. a watchdog that never
   fires (silent loss of protection, no visible symptom).
7. **Enabling `WDT_INTR_EN` without a handler that clears it** ⇒ interrupt storm
   at first expiry, then a reset anyway (§8).
8. **Asserting the `SW_RST3` bits instead of clearing them.** Writing to `0xF0`
   (set) rather than `0xF4` (clear) holds the block in reset: the dog stops
   counting. No reboot loop, but no protection either, and `WDT_CCVR` reads will
   be meaningless. Note the vendor DT lists the *set* offset first in each triple
   — an easy transcription inversion.
9. **Gating the counter clock off and not back on** (`CLK_EB0` bit 14 clear) —
   same silent-loss outcome. Because #80's periph clock driver does not yet
   register the WDT gates, a `clk_disable_unused()` sweep cannot currently reach
   them; once #80 adds them, they will need `CLK_IS_CRITICAL` or a real
   `clk_prepare_enable()` from this driver, or the core will gate the running
   watchdog off at late init.
10. **Clearing `COMM_ABORT_CFG`.** Nothing in a normal port does this, but a
    "reset the syscon to a known state" helper would: with bit 7 clear the dog
    expires and the SoC ignores it, so both the watchdog *and* `reboot` stop
    working while everything looks healthy.
11. **`reboot` silently not rebooting**, because mainline PSCI wins over the
    restart-handler chain and TF-A's `SYSTEM_RESET` is a stub (§10 item 11).
    Cost: an A/B rollback scheme that relies on `reboot` never completes.
    Test `reboot` explicitly on the first successful boot.

## 12. Open questions (do not guess these — measure them)

- **Is the reset really at 2× the programmed timeout?** Two independent vendor
  code paths say so; the hardware has never been observed reaching stage 2.
  Measure: disable the interrupt, program a short timeout, time the reboot.
- **Does `WDT_INTR_EN` = 0 collapse two stages into one?** Affects the U-Boot
  budget (30 s vs 60 s).
- **Does the `WDT_TORR_LOAD` strobe reload the running counter, or only latch the
  reload value?** Read `WDT_CCVR` across a strobe without a kick.
- **What is at slot `0x48`?** The `0xC` stride predicts a register there; the
  vendor never touches it. A status/"stage" register would be the natural
  occupant.
- **Are the `{value, set, clear}` aliases inside the watchdog block real?**
  §2.1 is inference from the SoC's house style, not measurement.
- **wdt2's counter-clock gate state out of reset** (§9.2).
- **Whether the boot ROM enables `WDT_EN` before the SPL runs** (§9.1).

## 13. Hardware verification of this spec (2026-09-06)

Read-only register reads and two brief, restored writes on the running vendor
system, before any of this was turned into a driver. Everything below is now
**V (measured)** rather than V-from-source, and one number in §3.1 changes.

**The counter clock and its mux (§3.1, §7).** With `WDT_TORR` temporarily
widened to `0xFFFF` so the count could not wrap inside a sample window,
`WDT_CCVR` was read twice three seconds apart on each mux setting:

| periph `CLK_MUX0` bit 19 | ticks elapsed | interval | rate |
|---|---|---|---|
| set (via `0x048700A8`) | 72 142 347 | 3.005 s | **24.007 MHz** |
| clear (via `0x048700AC`) | 98 545 | 3.005 s | **32.79 kHz** |

So bit 19 really is `CLK_WDT0_SEL`, the fast source really is 24 MHz, and the
slow source is the **32768 Hz** RTC output — the vendor driver's hard-coded
32 000 is 2.3 % low, as §3.1 inferred. `TORR` and the mux were restored to
`0x2B` / cleared afterwards and the block left enabled.

**Reload arithmetic (§3.2).** `WDT_CCVR` was observed at `0x2BC40D` with
`WDT_TORR` = `0x2B`: the reload is `(TORR << 16) | 0xFFFF`, and the counter's
top 16 bits track `TORR` exactly. Corroborated by the vendor's IRQ rate — the
running system showed 6 `ax_wdt` interrupts per CPU over 567 s of uptime, i.e.
one per ~94 s against the 86 s that `0x2B << 16` at 32768 Hz predicts.

**The periph syscon bits (§7).** Read back live: `CLK_MUX0` = `0x0007BFDE`
(bits 19/20 clear — the vendor kernel selects the slow source at probe, which
is *not* the state U-Boot leaves), `CLK_EB0` = `0x0003FEFF` (bits 14, 15 set),
`CLK_EB3` = `0x001F3FEF` (bits 19, 20 set). Every position the spec predicts is
where it says it is, and all four gates are open before Linux touches them.

**`COMM_ABORT_CFG` (§6.2).** Reads `0x000002C0` — bits 6, 7 and 9, exactly as
§6.2 says the boot chain leaves it. `COMM_ABORT_STATUS` reads `0x00000000` on a
normal boot, so it is not usable as a boot-reason source without first
establishing what sets it.

**The alternative reset (§6.3).** Writing `COMM_ABORT_CFG` bit 0 (`CHIP_RST_SW`)
resets the SoC through the entire boot chain and returns to a normal system in
about 50 s. `TOP_CHIPMODE_GLB_BACKUP0` survives it with spare bits intact,
which is what makes the milestone-bit channel in
[mainline-port.md](../../mainline-port.md) usable after a watchdog reset as
well as after an orderly reboot. This is now the board's primary reboot path, as
a mainline `syscon-reboot` node.

**Still open.** The §12 questions are unchanged: nothing here observed the block
reaching its second stage, so "reset at 2× the programmed reload" remains
inferred. The driver is built to be safe either way — it pets every 5 s
regardless of the timeout it advertises.

### 13.1 The periph alias offsets, independently confirmed (2026-09-06, later)

The four set/clear alias pairs this driver programs every boot — `CLK_MUX0`
`0xa8`/`0xac`, `CLK_EB0` `0xb0`/`0xb4`, `CLK_EB3` `0xc8`/`0xcc`, `SW_RST3`
`0xf0`/`0xf4` — were derived here from the vendor driver's DT specifiers and
then confirmed by the hardware behaving as predicted. They have since been
**re-derived from two artifacts that know nothing about this file**, during the
#76 reset-model work: the 10-cell reset specifiers' embedded clock triples, and
the reset register pairs harvested across all 445 specifiers.

All four fall out of a single rule for this controller —
`set = 0xa8 + 2 × value_offset`, `clr = set + 4` — which also places
`SW_RST0..3` at value words `0x18`/`0x1c`/`0x20`/`0x24` and therefore aliases
`0xd8`/`0xe0`/`0xe8`/`0xf0`. The reset harvest found `0xd8`, `0xe0` and `0xe8`
directly; this driver uses the fourth. That is complete coverage of the four
reset words from two independent directions.

Worth stating because it is the strongest evidence in this document: a rule
that *could* have failed against four live-verified numbers did not. The periph
register positions are no longer an inference chain — they are the intersection
of the vendor DT, an independent derivation, and a running driver.

Note the rule is **not** SoC-wide. There are three alias families: a `+4`/`+8`
triplet (pllc, comm), the contiguous alias array above (dispc, mm, periph, vpu),
and address-bit aliasing (cpu, flash). A port that assumes one family will
mis-address the other two.
