Issue #80. Written 2026-09-06 from the GPL-2.0 vendor 4.19 clock sources plus a
read-only capture of the running device. This is a data specification: a driver
author needs nothing from the vendor tree beyond this file.

(`.../linux/linux-4.19.125`). Citations are `clk-ax620e.c:NNN` (=
`$K/drivers/clk/axera/clk-ax620e.c`), `clk.c:NNN` (=
`$K/drivers/clk/axera/clk.c`), `ax620e-clock.h:NNN` (=

64 KiB `reg` window (V, `AX620E_clk.dtsi:8-59`). `#clock-cells = <1>`

### 1.2 ID reconciliation: 493 declared, 246 registered

- V: 21 + 162 + 47 + 14 + 52 + 20 + 43 + 122 + 12 = **493** IDs in
  `ax620e-clock.h`. The nine `#define`d namespaces are independent — the same
  numeric cell means different clocks under different phandles.
- V: the driver's tables hold **246** entries: 1 PLL + 9 fixed-rate +
  80 fixed-factor + 50 muxes + 86 gates + 20 dividers. (Mechanically counted per
  array; the `pll_cfg_array` block at `clk-ax620e.c:56-65` contains one live
  entry and five commented-out ones.)
- V: `clk_summary.txt` has **247** clock rows. 246 of them are the driver's;
  the 247th is `sysclk`, a DT `fixed-clock` at 10 MHz
  (`AX620E.dtsi:127-132`) with no consumer anywhere in the tree.
  **The "247 registered" figure in `docs/mainline-port.md` is the debugfs row
  count, not the driver's clock count.** Use 246.
- **Method for "unused/reserved"** (I, but mechanical): an ID is unregistered iff
  its macro appears in `ax620e-clock.h` and in no initialiser in
  `clk-ax620e.c`. 247 of the 493 IDs are unregistered. Two whole namespaces —
  `ddr` (47) and `isp` (20) — have zero registered clocks: `ddr` has no DT node
  at all, `isp` has a node but no driver.

**Why this matters for mainline:** many `clocks =` phandles in `AX620E.dtsi`
point at *unregistered* IDs. `of_clk_src_onecell_get()` returns the `NULL`
pointer from the `kcalloc`'d table (V, `clk.c:61,66`), `clk_get()` hands that to
the consumer, and every `clk_prepare_enable()` on it is a silent no-op. Confirmed
NULL references include `periph:AX620X_PCLK_CE_EB`, `periph:CLK_SPI_M{0,1,2}_EB`
and their `PCLK_`s, `periph:CLK_DW_DMA_EB`, `periph:CLK_TIMER1_EB` /
`PCLK_TIMER1_EB`, all `periph:CLK_TMR32_*` / `PCLK_TMR32_*`, all
`periph:*PWM*`, `flash:CLK_SPI_S_EB`, `flash:HCLK_SPI_S_EB`,
`flash:ACLK_AX_DMA_EB` / `PCLK_AX_DMA_EB`, `flash:CLK_GZIPD*`,
`cpu:HCLK_SPI_EB` (V, `AX620E.dtsi:718,973,1005,1038,1217,1236,1255,1273,1291,1355,1386,1877` and the header).
Those peripherals work anyway because the vendor drivers poke the syscon
themselves (§7).

### 1.3 Register-window conventions

The clock syscons expose each writable control word three ways: a plain
read/write word, a write-1-to-set alias, and a write-1-to-clear alias. **The
alias layout differs per controller.**

| Controller | Value reg | Set alias | Clear alias | Evidence |
|---|---|---|---|---|
| pllc `0x2210000` | `off` | `off+0x4` | `off+0x8` | V — `clk.c:530,532,535,542,552,573`; corroborated by `CPUPLL_CFG0`=0xC4 / `CPUPLL_CFG1`=0xD0 being 0xC apart (`clk-ax620e.c:41-42`) |
| common `0x2340000` | `off` | `off+0x4` | `off+0x8` | I — the registered offsets 0x00, 0x0C, 0x18, 0x24, 0x3C, 0x48 are exactly a 0xC stride, i.e. MUX0/MUX1/MUX2/EB0/(EB1=0x30)/DIV0/DIV1 |
| cpu `0x1900000` | `off` | `off+0x1000` | `off+0x2000` | V — `sdhci-axera.c:110-118` |
| flash `0x10030000` | `off` | `off+0x4000` | `off+0x8000` | V — `sdhci-axera.c:96-107` |
| periph `0x4870000` | `off` | table below | table below | V — `ax_cipher_device.c:39-56`, `8250_axera.c:44-51`, `gpio-axera.c:48-55`, `i2c-designware-platdrv.c:39-47`, `spi-dw-mmio.c:46-51` |

periph aliases (V): MUX0 `0x00`→`0xA8`/`0xAC`; EB0 `0x04`→`0xB0`/`0xB4`;
EB1 `0x08`→`0xB8`/`0xBC`; EB2 `0x0C`→`0xC0`/`0xC4`; EB3 `0x10`→`0xC8`/`0xCC`;
RST0 `0xD8`/`0xDC`, RST1 `0xE0`/`0xE4`, RST2 `0xE8`/`0xEC`, RST3 `0xF0`/`0xF4`
(RST aliases corroborated by `AX620E.dtsi` reset phandles such as
`<&periph_reset_ext 21 0xE8 21 0xEC>`). DIV0 `0x14`→`0xD0`/`0xD4` is **I** by
continuation of the pattern and has no direct citation. **GAP:** the alias
scheme for `dispc`, `mm`, `vpu` and `isp` is unknown; their registered value
offsets are a flat 4-byte stride (0x0, 0x4, 0x8, 0xC), so they cannot be using
the pllc/common triplet.

The vendor CCF driver **never uses the aliases**: every gate is a plain
read-modify-write on the value word (`clk.c:344-346, 373-375`), and every gate
entry passes `set_offset = clr_offset = 0` (V, all 86 rows). A mainline driver
should prefer the set/clear aliases where they are known, because RMW on a
shared word races the vendor-style direct pokes that firmware and other
subsystems still do.

## 2. The complete clock table

### 2.0 Type semantics (read this before the tables)

**Gates** (all 86). `gate_flags` is 1 for every single one (V). Semantics:
enable = set `BIT(bit)` in the value word, disable = clear it, `is_enabled` =
read the bit. Active-high, no inversion anywhere. Maps 1:1 onto
`clk_hw_register_gate()` with `flags = 0` (no `CLK_GATE_SET_TO_DISABLE`,
no `CLK_GATE_HIWORD_MASK`). The two other `gate_flags` encodings in the vendor
code (2 = inverted set/clear pair, 0/else = plain set/clear pair,
`clk.c:341-355`) are dead on this SoC.

**Muxes** (all 50). `clk_register_mux_table()` with `table = NULL`,
`mux_flags = 0`, `mask = BIT(width)-1` (V, `clk.c:134-142`). Register value ==
parent index, no remap. Note that several muxes have fewer parents than the
field can encode (e.g. width 3 with 5 or 6 parents); an out-of-range field
value makes `clk_mux_get_parent()` fail. Every observed field on the device is
in range (§4).

**Dividers** (all 20) are *not* `clk_divider` — they are a small Axera-specific
type (`clk.c:163-293`). Two facts define them:

1. **Divider map** (V, `clk.c:255-268`): a generated `clk_div_table` where
   `val = 0 → ÷1` and `val = n (n ≥ 1) → ÷2n`. So the sequence is
   1, 2, 4, 6, 8, 10, … up to `÷(2·(2^width − 1))`. Only ÷1 is odd.
   Rounding is `CLK_DIVIDER_ROUND_CLOSEST` (V, `clk.c:187-188,196-197,207-208`).
2. **Update handshake** (V, `clk.c:214-223`): write the divider field, then
   pulse the register's `update` bit — set it, wait 1 ms, clear it. Every
   divider's `update_offset` equals its `offset`, i.e. the update bit lives in
   the same word as the field.

Device confirmation of the map: `clk_dpu_out_divn` = 29.7 MHz from a 118.8 MHz
parent (÷4 ⇒ val 2), `clk_i2s_ref0_divn` = 12.288 MHz from 24.576 MHz (÷2 ⇒
val 1) (V, `clk_summary.txt`).

**Flags.** Only two CCF flags appear in the whole table: `CLK_SET_RATE_PARENT`
and `CLK_IGNORE_UNUSED`. **Nothing is marked `CLK_IS_CRITICAL`** (V). Every mux
and every divider carries `CLK_SET_RATE_PARENT | CLK_IGNORE_UNUSED`; gates vary
and are listed per row. The fixed-rate and fixed-factor clocks carry flags 0
except the six `cpupll_*` factors, which carry `CLK_SET_RATE_PARENT`.

## 3. CPUPLL — the one runtime-programmed PLL

### 3.1 Register map (all offsets from `pllc_clk` base `0x0221_0000`)

| Register | Value | Set alias | Clear alias | Contents |
|---|---|---|---|---|
| `CPUPLL_STS` | `0x0C0` | — (read-only) | — | bit 0 = PLL locked |
| `CPUPLL_CFG0` | `0x0C4` | `0x0C8` | `0x0CC` | bits [25:2] = `fbk_fra`, the 24-bit fractional numerator |
| `CPUPLL_CFG1` | `0x0D0` | `0x0D4` | `0x0D8` | [8:0] `fbk_int`; [14] `ldo_stb_x2_en`; [18:17] `pre_div`; [24:23] `post_div` (log₂) |
| `GRP_PLL_RDY_STS` | `0x1C0` | — (read-only) | — | per-PLL ready; bit 3 = CPUPLL |
| `CPUPLL_ON_CFG` | `0x1E8` | `0x1EC` | `0x1F0` | bit 0 = PLL enable |
| `GRP_PLL_RE_OPEN` | `0x230` | `0x234` | `0x238` | per-PLL "re-open" gate; bit 3 = CPUPLL |

V: `clk-ax620e.c:27-46,58` for the offsets, reference frequency and re-open bit;
`clk.c:479-485` for the field offsets; `clk.c:519,594-596` for the field widths
(`GENMASK(24,23)`, `GENMASK(25,2)`, `GENMASK(8,0)`); `clk.c:530,532,535,542,544,552,573`
for the +4/+8 set/clear aliasing.

Reference clock: **12 MHz**, hard-coded as `CPUPLL_REF_FREQ`
(`clk-ax620e.c:44`), matching the declared parent `cpll_12m` (V). Note that the
driver uses the constant, not `parent_rate` — port it as `parent_rate` in
mainline.

### 3.2 Rate formula

Implemented (integer-N only), V `clk.c:594-601`:

```
post_div_shift = CFG1[24:23]
post_div       = 2 ^ post_div_shift
rate           = fbk_int * (REF / post_div)          REF = 12 MHz
```

The full fractional form is present but commented out in both the write and the
read path (V, `clk.c:522-527,546-549,598-599`):

```
rate = (fbk_int + fbk_fra / 2^24) * (REF / post_div)
```

`pre_div` is **written as 0 and never used in any rate computation** (V,
`clk.c:515,539`). **GAP:** whether `pre_div` encodes ÷1 at 0 or ÷(n+1) is not
determinable from the source. The device's 1.2 GHz with `fbk_int` = 100 and
REF = 12 MHz proves the effective reference divide is 1 at `pre_div` = 0 (I).

`ldo_stb_x2_en` (CFG1 bit 14) is always written 1 and is not a rate field (V).

**VCO / refdiv limits:** the only bounds in the source are
`CPUPLL_MIN_RATE = CPUPLL_MAX_RATE = 1 500 000 000` (V,
`clk-ax620e.c:45-46`), pushed into the CCF rate range via
`clk_hw_set_rate_range()` (V, `clk.c:662`) and clamped in `round_rate` (V,
`clk.c:609-613`). **These are wrong for the AX630C**, which boots at 1.2 GHz;
1.5 GHz is the AX631 part's ceiling (`axera-cpufreq.c:14`). **GAP:** no VCO
range, no lock time, no minimum/maximum `fbk_int` is documented anywhere in the
vendor tree. Treat 1.2 GHz as the AX630C maximum (`axera-cpufreq.c:12`,
`AX620E_opptable.dtsi:39-41`) until measured.

### 3.3 Programming sequence

Described from `clk.c:502-575`; the whole body runs under one global spinlock.

1. Clear the group re-open bit: write `BIT(3)` to `0x238`.
2. Turn the PLL off: write `BIT(0)` to `0x1F0`.
3. Clear the CFG1 fields about to be rewritten: write
   `BIT(14) | BIT(17) | BIT(18) | GENMASK(8,0)` to `0x0D8`. (The source also
   ORs `BIT(23)` when the decoded `post_div` is 0 — unreachable, since
   `post_div = 2^n ≥ 1`.)
4. Write the new CFG1 fields to the set alias `0x0D4`:
   `(fbk_int << 0) | (0 << 17) | (1 << 14) | (0 << 23)`.
5. Clear `GENMASK(28,2)` in CFG0 via `0x0CC` — this wipes `fbk_fra` (and bits
   28:26, purpose unknown). Because the fractional write-back is commented out,
   **every programmed rate is integer-N**.
6. Turn the PLL on: write `BIT(0)` to `0x1EC`. Delay 50 µs.
7. Poll `CPUPLL_STS` (`0x0C0`) bit 0 for lock — a bare 10 000-iteration spin
   with no delay and no time-based timeout; on exhaustion it only prints.
8. Poll `GRP_PLL_RDY_STS` (`0x1C0`) bit 3 — same bounded spin.
9. Set the group re-open bit: write `BIT(3)` to `0x234`.

**There is no safe-parent dance.** The vendor never reparents `clk_cpu_sel` away
from CPUPLL before stopping it. That happens to work today only because CCF's
`clk_change_rate()` walks parents before children, so a transition *into* the
1.2 GHz OPP relocks CPUPLL while the CPU is still fed from `npll_800m`. A
`clk_set_rate()` on a CPU already running from CPUPLL would stop the clock
feeding the running core. **A mainline driver must switch `clk_cpu_sel` to a
safe parent (`cpll_24m` or `npll_800m`), relock, then switch back** — either
inside the PLL's `set_rate` or via a `notifier`/`CLK_SET_RATE_GATE` scheme.

### 3.4 OPP cross-check

`cpu_opp_table` (V, `AX620E_opptable.dtsi:23-42`) and the mux parents of
`clk_cpu_sel` line up exactly:

| OPP | Source | `clk_cpu_sel` index | CPUPLL touched? | CFG1 value |

| 24 MHz | `cpll_24m` | 0 | no | — |

## 5. Bring-up subset (issue #76)

### 5.1 What is already running before Linux touches anything

CPUPLL is the only PLL whose rate the driver reads back from hardware, and it
reads **1 200 000 000** — proof the SPL programmed it (V, `clk_summary.txt`).
The other seven PLL rates are table constants, so the dump cannot prove
firmware set them; but the SoC is booting from eMMC over a 200 MHz card clock
sourced from `npll_400m`, running a 115200 console off `cpll_208m`, and
negotiating Ethernet off `epll_25m`/`epll_50m` — none of which the vendor clock
driver programs. **Conclusion (I, well supported): U-Boot/SPL brings up CPLL,
CPUPLL, NPLL, EPLL, HPLL, DPLL and both VPLLs, and sets every top-level mux and
divider. A first mainline boot can model all eight PLLs as `fixed-clock`/
`fixed-factor` and never write a PLL register.**

Practically, `#76` can ship a driver that registers only fixed-rate roots,
fixed-factor dividers, the muxes it needs read-only, and the gates below — and
nothing will regress, because nothing on the boot path depends on the driver
*changing* a rate.

## 6. Recommended mainline shape

**One driver, one compatible per controller, match data selects the table.**
Nine `CLK_OF_DECLARE`s over two files is the wrong shape. Use a single
`platform_driver` whose `of_device_id` table carries a `struct ax630c_clk_desc *`
per compatible: `{ num_clks, fixed_rate[], fixed_factor[], mux[], div[], gate[],
pll[] }`. That is ~200 lines of code and ~1200 lines of table.

**`CLK_OF_DECLARE` vs platform driver.** Use a platform driver
(`builtin_platform_driver` + `of_clk_add_hw_provider(dev, of_clk_hw_onecell_get,
…)`). Nothing on this SoC needs clocks before `timekeeping_init()` — the
architected timer takes its frequency from DT, and the earlycon is
`uart8250,mmio32` with a fixed divisor (V, `cmdline-model.txt`). Dropping
`CLK_OF_DECLARE` also gets rid of the vendor's registration-order landmine:
`common_clk` registers `cpupll_1200m` naming a parent `"cpupll"` that
`pllc_clk` only creates later, so it starts life as an orphan and is
reparented behind CCF's back (V, `AX620E_clk.dtsi` node order + `clk.c:66`).
With one driver you can register `pllc` first, or better, use
`clk_parent_data`/`clk_hw` parents instead of global name strings.

**Binding.** Keep `#clock-cells = <1>`, keep the nine per-controller
namespaces, and keep the existing numeric values. There is no ABI to preserve —
this is a fresh mainline binding — but the vendor numbering is dense,
already carved per controller, and matches a register/bit ordering that is
useful to preserve (§7). Re-numbering buys nothing and makes every future
diff against vendor DT harder. Concretely:

- `compatible: axera,ax630c-cpu-clk` (etc.), plus `syscon` — these windows carry
  reset and pinmux-adjacent registers too, so other drivers legitimately need
  `regmap` access to them; the clock driver should itself use
  `syscon_node_to_regmap()` rather than a private `ioremap`, so it shares the
  lock with the reset driver of #76.
- Drop `axera,ax620x-isp-clk` and the whole `/*ddr clk*/` namespace from the
  binding — neither has ever had an implementation.
- One `dt-bindings/clock/ax630c-clock.h` with the nine namespaces prefixed
  `AX630C_`; delete `AX620X_CPUPLL` (never registered) and the seven dead PLL
  cells.

**What to drop from the vendor model:**

- `CLK_IGNORE_UNUSED` everywhere (workaround, not description). Replace the
  genuinely-must-run ones with `CLK_IS_CRITICAL`.
- The Axera divider type. Its behaviour is `clk_divider` with a
  `clk_div_table` (1, 2, 4, 6, … 2·(2^w−1)) plus a post-write update pulse.
  Either build the table statically and add a thin `set_rate` wrapper for the
  update bit, or note that `CLK_DIVIDER_READ_ONLY` is enough for #76 — nothing
  on the boot path changes a divider except eMMC/SD.
- The custom gate type. `clk_hw_register_gate()` with flags 0 is exactly
  equivalent for all 86, and mainline's gate can use the set/clear aliases via
  `CLK_GATE_HIWORD_MASK`-style handling or a small `regmap` gate.
- The 12 duplicate copies of the `TOP6` parent array, the `vpll0` override, the
  commented-out PLL rows, `sysclk`, `clk.c`'s unused `axera_clk_alloc()` and the
  `axera_clk_unregister_*` macro family.
- 15 clocks that are registered but consumed by nothing at all (`clk_vi_eb`,
  `clk_tmr_sync_eb`, the five `need_modify` dispc gates, `clk_cs_apb_eb`,
  `clk_cpu_24m_eb`, `clk_lpc_{flash,mm,peri,vpu}_eb`, `clk_dphy{rx,tx}_tlb_eb`,
  `MCLK1..5_eb` on this board) — keep the IDs, but they need no urgency.

**What to add:** a real 24 MHz crystal root; `CLK_SET_RATE_GATE` or a safe-parent
switch around CPUPLL (§3.3); `clk_parent_data` so parents resolve by index, not
by global string; and `assigned-clocks`/`assigned-clock-parents` in DT for the
handful of muxes the board needs pinned (`clk_uart_sel` → `cpll_208m`,
`clk_emac_rgmii_tx_sel`, `rgmii_ephy_clk_sel`).

## 7. Appendix: recovering the unregistered IDs

The header's IDs are a **dense descending-bit enumeration per register**: within
one control word, consecutive IDs occupy consecutive bit positions counting
down. Given one anchor per register, every ID in it is recoverable.

The rule is **V**, confirmed independently at eleven anchor points across five
vendor drivers and the CCF table itself:

| Anchor | Source |
|---|---|
| periph `clk_i2c_mst0_eb` = 0x08 bit 8 | `i2c-designware-platdrv.c:44` (`BIT(8 + id)`) |
| periph `pclk_i2c_mst0_eb` = 0x0C bit 17 | `i2c-designware-platdrv.c:47` |
| periph `clk_gpio0_eb` = 0x08 bit 4 | `gpio-axera.c:53` |
| periph `pclk_gpio0_eb` = 0x0C bit 13 | `gpio-axera.c:56` |

Every one of those falls exactly where the descending-ID rule predicts from the
